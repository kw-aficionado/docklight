Template schema

A server template describes a container image, settings, ports, lifecycle and optional protocols. For API compatibility, it is stored under the gameskill resource name and uses one top-level gameskill: YAML mapping. Imports are limited to 512 KiB.

The parser rejects unknown fields and duplicate mapping keys with an error. This catches misspelled settings such as done_regx before a template is saved; arbitrary keys remain valid only inside declared environment and sysctl maps.

Supported shape

gameskill:
  id: sample-app
  name: Sample App
  category: Apps
  version: 1
  description: Example containerized app
  docker:
    image: example/app:1
    data_path: /data
    user: "0:0"
    keep_entrypoint: true
    env:
      APP_MODE: "{{MODE}}"
    extra_volumes: [/var/lib/app]
  variables:
    - key: MODE
      name: App mode
      type: select
      options: [production, maintenance]
      default: production
      required: true
  update:
    image: example/app-cli:1
    label: Update app
    script: /usr/local/bin/update
    app_writable:
      - uploads
  startup:
    exec: [serve]
    done_regex: "ready on"
    stop: stop
    save_command: save-all
    stop_timeout: 30
  ports:
    - name: web
      default: 8080
      protocol: tcp
  stack:
    services:
      - name: database
        image: mariadb:11
        data_path: /var/lib/mysql
        user: "0:0"
        resource_weight: 1
        env:
          MARIADB_DATABASE: "{{DB_NAME}}"
          MARIADB_PASSWORD: "{{DB_PASSWORD}}"
  query:
    type: a2s
  rcon:
    enabled: false
  bans:
    ban_command: "ban {{player}} {{reason}}"
    unban_command: "pardon {{player}}"
  watchers:
    - name: Startup warning
      pattern: "(?i)failed to bind"
      threshold: 1
      window_secs: 60
      action: notify
  restart:
    warnings:
      - at: 5m
        msg: say Server restart in 5 minutes.
      - at: 1m
        msg: say Server restart in 1 minute.

docker.image is required. At least one of startup.command, startup.exec, or docker.keep_entrypoint: true is required.

FieldBehavior
id, name, category, version, description, author, iconTemplate metadata. IDs use lowercase letters, digits, hyphens, and underscores.
docker.imageImage to pull for server startup.
docker.data_pathContainer path backed by the server app-data directory; defaults to /data. For stack templates the main app gets only <server data directory>/_app, leaving sidecar data outside its mount.
docker.userOptional container UID:GID or username. Without keep_entrypoint, the panel sets a UID and mounts a minimal passwd shim.
docker.keep_entrypointIf true, Docker keeps the image entrypoint and startup.exec is passed as its arguments. Otherwise Docklight replaces the image entrypoint with the declared startup.exec executable or /bin/sh -c for startup.command. The passwd shim is skipped when the image entrypoint is kept.
docker.envAdditional main-app environment values with literal {{KEY}} substitutions. Single-container templates also receive declared variables; stack templates should map the variables the main app needs here. Panel-reserved values are injected in both cases.
docker.extra_volumesExtra container paths backed by subdirectories in this server's data directory. Protected system paths are rejected.
docker.capabilitiesRestricted allowlist: NET_ADMIN, NET_RAW, NET_BIND_SERVICE, SYS_NICE.
docker.devicesRestricted host device allowlist: /dev/net/tun, /dev/dri, /dev/fuse; optional container path and rwm permissions.
docker.sysctlsRestricted allowlist for selected forwarding sysctls.
variablesForm fields of type string, int, bool, or select; optional default, required, min/max, pattern, secret, and hint.
config_filesUp to 64 safe, relative file paths. Existing files appear as shortcuts in the Files tab; .properties, .env, .cfg, and .conf support a key/value form and a raw editor. Missing files are skipped.
install.image, install.scriptOptional temporary install container and shell script. The script runs as root with the data mounted at /data.
update.image, update.script, update.labelOptional app-update tool container, required shell script when the block is present, and button label (defaults to Update app). The image defaults to docker.image; the script runs as root with app data mounted at /data and declared environment values available. Read secrets from the environment; secret placeholders in the image or script are rejected. The panel captures and redacts declared secrets from output.
update.app_writable[]Optional list of up to 64 clean paths relative to app data. After the update, Docklight changes file ownership to the panel user without changing group ownership, and adds group-write permission only under these paths. The data root itself is ignored.
startup.commandShell string run with /bin/sh -c when the image entrypoint is replaced.
startup.execArgument list for the container command. When keep_entrypoint is true these are image entrypoint arguments; otherwise the first item becomes the executable and remaining items are its arguments.
startup.done_regexRegular expression searched in recent container output to mark startup ready.
startup.stop, startup.save_commandCommands sent to container input before Docker's graceful stop.
startup.stop_timeoutGrace period in seconds before Docker kills the container. Defaults to 30.
restart.warnings[]Optional countdown points for scheduled restarts. at is a Go duration up to 24 hours; msg is a complete console command sent through RCON when available, then stdin. {{server_name}}, {{minutes}}, and {{seconds}} are available.
portsContainer ports to publish. Protocol is tcp, udp, or tcp+udp; a free host port is allocated from config. A port named rcon binds to loopback.
steam{ app_id, anonymous } enables SteamCMD install behavior. Steam ports use the declared container port as the host port (1:1); app data is made writable; the installer receives /steamcache as HOME and mounts the persistent SteamCMD cache there. With anonymous: false, an admin must authorize a Steam account under Templates → Steam account; STEAM_USER is injected into the installer. The template's script passes app_id to SteamCMD itself.
stack.services[]Optional list of 1–8 sidecars started on a dedicated network for this server. Each service requires a DNS-safe name and image. data_path is optional for stateless workers; when present it binds persistent, backup-covered data. extra_volumes adds more persistent container paths. enabled, user, command, env, and resource_weight are optional.
stack.services[].extra_volumesAdditional absolute, validated container paths backed by _stack/<service>/_extra/<path>; included in server backups and kept outside the main app's file root. Duplicate and protected system paths are rejected.
stack.services[].enabledOptional templated boolean. Empty means enabled; true/1/yes/on and false/0/no/off are accepted. An unresolved placeholder disables the service so new opt-in services stay off for older servers.
stack.services[].envSidecar-only environment values. {{KEY}} references declared template variables; secret values are decrypted only for the containers that use them. Secrets are rejected from image references and command arguments.
stack.services[].resource_weightRelative CPU and memory share when server limits are set. Main app weight is 3; sidecars default to 1 and may set 1–100. All containers share the one server limit.
query.typeminecraft, minecraft-java, minecraft-bedrock, a2s, or source.
rconEnables RCON commands using a declared password_var. The host mapping is loopback-only when its port is named rcon.
bans.ban_command, bans.unban_commandOptional pair of single console commands used by the central ban list. Both must include {{player}}; {{player_id}} and {{reason}} are also available. Docklight removes control characters before sending commands over RCON or server input.
bans.adapterOptional built-in adapter dayz-ban-file. It writes the player's 17-digit SteamID or 44-character UID as a line in the server data root's ban.txt; do not also declare command fields. This adapter does not kick an already-connected player.
watchers[]Optional template-seeded log watcher defaults. Each entry has a unique name, Go RE2 pattern, threshold (default 1, maximum 1000), window_secs (default 60, maximum 3600), and action (notify or advisory; legacy kvasir imports as advisory). Rules are copied on server creation and installation. Operator edits persist across installs; deleted template rules are restored on the next install. Hosted-provider log consent is never copied from a template.
anticheat.antixray, anticheat.battleyeOptional { supported, config_hint } informational cards in the server detail Anti-cheat tab. The tab requires server.files; Docklight does not apply the hint or modify server files.
anticheat.plugins_recommendedOptional list of up to 16 plugin names displayed as template guidance only.

Variable keys that conflict with panel-injected names (including SERVER_NAME, HOME, PUID, PGID, UID, GID, PUBLIC_URL, PORT_*, and *_PORT) are rejected. Secret variables are encrypted at rest and masked in API responses. Password/token/secret/private-key-like variable names are treated as secret even without secret: true.

The Steam-specific variable STEAM_USER is reserved and cannot be declared by a template. Steam account setup and cache behavior are described in the Steam account guide.

An update block adds an admin-only Update app action to installed servers and an audited POST /api/servers/{id}/app-update endpoint. Docklight stops the main app, runs the tool container, then recreates and starts the app even if the update script exits with an error. For stack templates, the tool joins the server's private network; running sidecars are kept up, and stopped or missing sidecars are started before the tool runs. Scheduled Update actions use this app script synchronously and skip stopped servers; templates without the block keep the existing installer-based scheduled server update.

Validation and limits

When startup.done_regex is empty, a template with a query block is marked ready only after its configured game query responds. A template without either signal is marked ready when its container is running. A declared web port must also accept a local TCP connection.

The reader supports nested mappings, sequences, scalar values, inline lists, and literal/folded block strings. It is a bounded subset parser rather than a general YAML 1.2 implementation. Unknown fields in supported mappings are rejected, so use only fields listed here.

Container capabilities, devices, mounts, and sysctls are allowlisted to limit host access. config_files accepts up to 64 clean relative paths. The Files tab shows shortcuts for paths that exist; .properties, .env, .cfg, and .conf files support a key/value form and raw editing, preserving comments and unsupported lines. Rune-defined app-data import steps and backup hooks are not supported in this release. Private image access is managed by an administrator under Templates → Registry access; saved logins cover runtime images, sidecars, install images, and update pulls.

Seven built-in templates are embedded in the binary: Minecraft Java, Minecraft Bedrock, DayZ, Uptime Kuma, Vaultwarden, WordPress + MariaDB, and Cloudflare Tunnel. Built-in IDs cannot be overwritten or deleted. Community templates can be imported from the Templates page, subject to the same validation.

Sidecars receive a stable DNS alias equal to their service name, share only their server's user-defined bridge with the main app, and currently do not publish host ports. The main app receives only its _app data bind; persistent sidecar data stays under _stack/<service name>, outside the main app's filesystem and Files tab. Backups archive the full server data root and include both. The panel starts enabled sidecars in declaration order before the main app, stops them after the main app in reverse order, and removes them with the server. Startup install containers do not join the stack network; app initialization that needs a database belongs in the main app's runtime startup.

Catalog repositories

Administrators can save GitHub, Gitea, and Forgejo repositories from Templates → Catalog repositories. An empty host selects GitHub. Other hosts must be HTTPS base URLs; Docklight contacts only hosts named by saved repositories and does not follow redirects. A repository can set its own folder, branch or tag, and optional access token. Repository tokens and the optional panel-wide GitHub token are encrypted with auth.secret_key; a repository token is used only for that repository, and the panel-wide GitHub token is sent only to GitHub's API host.

The browser lists .yaml and .yml files up to 512 KiB and folders at the repository root plus one subfolder level. Successful folder listings are cached for 10 minutes. Catalog YAML passes the same parser and privilege checks as an upload. Installing a known ID updates that community template; built-in IDs are rejected. Each installed catalog template records its host, repository, file path, and ref. A manual YAML or Compose import of an existing catalog template clears that provenance and becomes the locally managed version.

Docker Compose import

Administrators can import one Compose YAML document from Templates → Import Compose. The API accepts a multipart file field and optional main service and display name; raw YAML is also accepted with main and name query parameters. Files are limited to 1 MiB. Docklight chooses a main service from published ports and common service names, or the administrator can name it explicitly. Other services with pullable images become sidecars on the private per-server network.

Short-form main-service ports are converted to container ports and Docklight allocates free host ports. Specific host-IP bindings are dropped because the panel cannot preserve them; localhost-only ports are never widened to all interfaces. Named volumes become Docklight-managed persistent paths on the main service and sidecars, but existing Compose volume contents are not copied. Bind mounts are reported as warnings and omitted from the template. After creating the server, an administrator can re-add each mount under Settings → Host mounts and select the matching main or sidecar container. Host folders are mounted in place, so their contents are not copied into Docklight-managed storage. The importer also reports dropped build, network, command, environment-file, health-check, dependency, and other unsupported settings. Compose interpolation is not evaluated. Values for environment keys that look secret are not stored; the template prompts for those values when creating a server. The importer validates and round-trips the generated template before saving it. Re-importing a non-built-in ID updates the existing template; built-in IDs are protected.

Pterodactyl egg and XML imports

Administrators can import one Pterodactyl egg JSON file or one XML <gameskill> document from Templates. Each upload is limited to 1 MiB and accepts either a multipart file field or a raw request body. The generated template is serialized and validated by the same Docklight parser before storage. Built-in IDs are protected; importing an existing community ID updates it and clears its catalog provenance.

Egg IDs are slugified from the name and start at version 1. docker_image is used unless docker_images supplies images, in which case the first key in sorted order is selected for repeatable imports. The egg startup command is preserved verbatim; the first config.startup.done value becomes a literal-quoted ready regex. Installation scripts use the egg's installation container or fall back to its runtime image. config.files keys are sorted into config_files. Variable rules map Laravel boolean, integer/numeric, and in:a,b to Docklight bool, int and select types; other rules become strings. No egg ports are inferred.

XML supports <gameskill> identity, description, author and icon fields; Docker image; typed variables; installation; startup; config_files; and ports. Version zero becomes one, an empty category becomes Imported, and an empty port protocol becomes tcp. Elements outside this subset are ignored. In both formats, defaults for variable names that look like passwords, tokens, secrets, private keys or credentials are removed and a warning is returned; secret values are never written to template YAML or import responses.

Check updates compares versions by template ID and reports a missing saved source or network error instead of treating it as current. It only lists; applying an update is an explicit administrator action. Checks do not run on startup or on a timer. No remote catalog is preconfigured: add a repository you trust before browsing or checking templates that do not have recorded source metadata. See the API reference for repository and GitHub token routes.

Private container registries

Administrators manage private image credentials from Templates → Registry access. Save one username and password or access token per registry hostname; Docker Hub spellings normalize to docker.io, and hostnames are lowercased. Docker image references are matched using Docker's registry split rules, so nginx:latest and team/nginx:latest use the Docker Hub login while ghcr.io/team/nginx:latest uses a ghcr.io login. Host and port must match for private registries.

Credentials are encrypted with auth.secret_key. Runtime app images, stack sidecars, temporary install images, and the ownership helper's Docker Hub image use the same per-pull lookup. The login test calls Docker Engine's auth-check endpoint. See access and security and the API reference.
