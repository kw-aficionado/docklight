# Server backups

Docklight stores snapshots of each server's data directory. Open a server's **Backups** tab to create, restore, delete, or prune snapshots. Local and object-store snapshots can also be verified in Docklight; use PBS verification jobs for Proxmox snapshots. Backups can be written to local panel storage or one configured remote destination: S3-compatible, Google Cloud Storage, Azure Blob Storage, SFTP, SMB, an rclone-supported cloud drive, or Proxmox Backup Server (PBS).

## Create and restore

Stop the server before creating or restoring a backup. Docklight checks the saved server state and, when a container is recorded, asks Docker to confirm that it is stopped. This avoids copying a live database or world save midway through a write.

Local and object-store backups are compressed, encrypted in authenticated chunks, checksummed, and verified before Docklight records them. Server data is streamed; the panel does not load one complete archive into memory. Symlinks and special filesystem objects are refused. Restore verifies the checksum and encrypted archive before extracting to a staging directory. It overlays archived files onto the existing data directory and leaves files absent from the archive untouched. If a file or directory conflicts with the archived path, or an unsafe filesystem object is present, restore stops and rolls back changes already made. PBS uses its own `.pxar` format and does not use Docklight-side archive encryption.

Local backups are stored under `<database directory>/backups/<server id>/` by default. Set `backups.path` to another local directory to place them on a mounted disk or filesystem. The panel creates backup directories with owner-only access and files with mode `0600`.

## Remote destinations

Administrators configure one remote destination from **Backup storage** in the Docklight sidebar. Only one protocol can be active at a time. The connection check lists the remote root when supported, uploads a temporary test file, reads it back, and removes it again. PBS is checked by listing its snapshots because PBS stores structured, deduplicated archives rather than individual objects. Credentials and the host or endpoint are encrypted with `auth.secret_key`; API summaries report whether credentials are saved without returning them.

SFTP uses password authentication on port `22` by default. Enter the server host, username, password, optional path prefix, and the server's SHA-256 host-key fingerprint. Docklight checks this pin during SSH negotiation before it sends the password and refuses a mismatch. Get the fingerprint from the SSH administrator or another authenticated channel; do not trust an unverified `ssh-keyscan` result. On an OpenSSH server, `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256` prints the Ed25519 host-key fingerprint when that is the key the server presents. For an RSA-only server, use its `ssh_host_rsa_key.pub` instead. The saved fingerprint is public metadata and is returned in the admin target summary; passwords remain encrypted and redacted.

After upgrading a Docklight instance that already had an SFTP target, enter its verified fingerprint in **Backup storage** before using that target. Existing backup records and encrypted credentials are preserved; the target is unavailable until the pin is set. To rotate a server key, verify the replacement fingerprint over a trusted channel and update the pin; recorded backup objects do not need to be deleted.

SMB uses NTLMv2 authentication on port `445` by default. Enter the host, share name, username, password, and optional path prefix. Create the share and grant the account access before testing the destination.

S3-compatible storage uses an HTTPS endpoint, bucket name, region, access key, secret key, and optional object prefix. Plain HTTP is accepted only for a loopback endpoint used by a local emulator. Docklight uses path-style requests and Signature Version 4; verify that the provider supports this S3 API mode. Allow `s3:PutObject`, `s3:GetObject`, `s3:DeleteObject`, and `s3:AbortMultipartUpload` for the configured prefix; create the bucket separately.

Azure Blob Storage uses an account name, existing container, account key or SAS token, and optional object prefix. Leave Endpoint blank to use `https://<account>.blob.core.windows.net`, or enter the account's Blob endpoint for a sovereign cloud. Account keys use Azure Shared Key authorization. SAS tokens must allow list, read, write, and delete access to the container; the token is encrypted and never returned by the API. Uploads stream as 16 MiB blocks and are limited to 800 GB per backup. Docklight does not create the container.

Google Cloud Storage uses an existing bucket, a service-account JSON key, and an optional object prefix. Docklight calls the native Cloud Storage JSON API with OAuth 2.0 service-account credentials; it does not use the S3 interoperability endpoint. Grant the service account object list, create, get, and delete access to the bucket or backup prefix. The JSON key is encrypted with `auth.secret_key`, never returned by the API, and used to obtain short-lived access tokens. Uploads stream in 16 MiB resumable chunks and support objects up to 5 TiB. Interrupted uploads are canceled. Create the bucket separately.

Rclone supports Jottacloud, Dropbox, OneDrive Personal, Google Drive, Box, pCloud, MEGA, WebDAV (including Nextcloud and ownCloud), and a custom rclone config section. For Dropbox, OneDrive, Google Drive, Box, and pCloud, run `rclone authorize <provider>` on a computer with a browser and paste its JSON token. Jottacloud accepts a single-use personal login token and exchanges it for its rotating OAuth credentials when saved. MEGA uses an email and password; two-step verification is not supported. WebDAV requires an HTTPS URL, service type, username, and password. Custom config accepts exactly one `[remote]` section with a `type = ...` option. Docklight builds the remote section and runs it in the pinned `rclone/rclone:1.75.2` container; `docker.rclone_image` can override that image. Rclone configuration is encrypted in SQLite, and updated OAuth tokens are written back encrypted after each helper run. Dropbox and Box can stream uploads; other backends may use temporary space inside the helper container for an archive-sized upload.

### Proxmox Backup Server

PBS targets use the server host, port (default `8007`), datastore, `user@realm!token` auth ID, API token secret, and optional namespace. Add the PBS server's SHA-256 certificate fingerprint when it uses a self-signed certificate. Grant `DatastorePowerUser` to both the user and its API token; PBS treats those ACLs separately and intersects their effective permissions. Use a dedicated token with access to the intended datastore. The client helper requires a Linux/amd64 Docker host. Build and publish the pinned helper image from [`deploy/pbs-client/`](../../deploy/pbs-client/), or set `docker.pbs_client_image` to an image you build and maintain.

Docklight sends each server to a PBS group named `host/<server-name>-<short-id>`. Renaming a server starts a new group. PBS receives the server data directory directly as a `.pxar` file archive so it can deduplicate chunks between snapshots. Docklight uses TLS and the PBS API token but does not add its own client-side archive encryption for PBS; protect the datastore and use PBS controls appropriate to your environment. The client may add `.pxarexclude-cli` to the server data directory. Metadata summaries are counted before the upload, so this helper file may be included in the archive without being reflected in the displayed file count.

Docklight prunes each recorded PBS group with `--keep-last` and `--keep-daily`, then lists the group and removes stale panel records. If prune or list fails, Docklight keeps the backup record and reports “Backup kept, but retention could not run.” Docklight does not download PBS snapshots or verify them in the panel; schedule verification jobs in PBS. Restore downloads the `.pxar` archive to a private staging directory, rejects symlinks and special files, then overlays the restored files onto the server data. Files absent from the snapshot remain in place. The server stays stopped after restore and must be started manually.

The server's **Backups** tab offers the configured remote protocol after an administrator enables it. For object stores and file servers, Docklight streams the encrypted archive to the destination, then downloads and verifies its checksum and archive contents before adding the database record. PBS uploads directly to its deduplicating file archive and relies on PBS verification jobs. S3 uses multipart uploads for larger archives. Object-store verification and restore use a mode-`0600` temporary file under panel server-data storage. Ensure that filesystem has enough temporary space for the backup being restored.

While remote backup records exist, Docklight locks the configured protocol, host, port, bucket or share, region, and prefix. Azure also locks the account name and endpoint; credentials and the authentication mode can be rotated. GCS locks the bucket and prefix while allowing the service-account key to rotate. Rclone locks the provider, account name when available, WebDAV endpoint, and prefix while allowing its saved credentials to refresh. PBS locks its host, port, datastore, auth ID, and namespace; its token secret and certificate fingerprint can be rotated. Delete those remote backup records before moving to another destination. Retention uses database records rather than listing remote storage, except PBS which must list snapshots after server-side pruning. Server deletion removes each recorded remote backup before deleting server data.

## Encryption key and recovery

Backup encryption derives its key from `auth.secret_key`. Keep that value, the SQLite database, and the backup files together. A new installation cannot decrypt these backups without the same secret key; changing or losing it also prevents decryption of stored server credentials and TOTP secrets.

## Retention

For local and object-store destinations, the default policy keeps the 10 most recent backups per server. Set `backups.retention` to a value from 1 to 100. PBS applies the configured count independently as `--keep-last` and `--keep-daily` for each server group. Creating a backup applies retention automatically. The **Prune to retention** action can also be run at any time. The API accepts an optional `keep` value from 1 to 100 for a one-off prune.

Deleting a server also removes its recorded backups from local and remote storage. Export any copies that must outlive the server before deleting it.

## Schedules

Open a server's **Schedules** tab to schedule a backup, start, stop, restart, update, console command, or message for one server. Administrators can also open **Manage → Schedules** to apply the same actions to a realm or all servers. Five-field (`minute hour day month weekday`) and six-field (seconds first) cron expressions use the panel host's local timezone. Schedules are enabled by default and keep the latest 100 run records; the UI shows the latest 50. Realm membership is read when a schedule fires, so moving a server changes the next run's targets. Each targeted server gets a separate result row. **Run now** queues one immediate execution, including for a disabled schedule. For a warned restart running in the background, a cron time due before completion is recorded as skipped and advanced to the next time. A run records its outcome, and backup retention applies after a successful backup. A backup schedule keeps its selected destination; if the remote destination is disabled, changed to another protocol, or unreachable, the run is recorded as a failure. The server must be stopped when a backup schedule fires; a running server produces a recorded failure and the next cron occurrence remains scheduled. A start on an already running server and a stop with no container are recorded as skipped.

Restart schedules can warn players using countdown commands declared in the template's `restart.warnings`. Choose a warning duration configured by that template, or turn warnings off to restart immediately. Scoped restart schedules offer only countdowns supported by every current target. Templates with a player-query protocol also offer **Skip if players are online** for restart and update schedules. If the query reports players, that target is skipped; if the query cannot return a count, Docklight proceeds and records the unavailable count. A warned restart runs in the background. If a manual action stops or replaces the server during its countdown, Docklight cancels the scheduled restart. An update stops the server, reruns its template installer against the existing data directory when one is configured, pulls the current server image, and creates a fresh container. Server data is retained. A scoped update waits for each server to return to running and stops dispatching updates after three consecutive failures; online-player skips do not count as failures.

A console-command schedule accepts one line, encrypts it at rest, and sends it through RCON or server stdin only while the server is running; the command itself is not shown in schedule or run-history responses. A message schedule is available on Minecraft Java and Bedrock; it selects a built-in or admin-created template and supplies its numeric placeholders. Template bodies are single Minecraft console commands and may use `{{server_name}}`, `{{minutes}}`, and `{{seconds}}`. Docklight snapshots the selected body and values in encrypted storage; editing or deleting a template does not change an existing schedule. Messages send only while the server is running and are not shown in schedule or run-history responses. Start, stop, restart, and update schedules need `server.schedule` and `server.control`; backup schedules need `server.schedule` and `server.backup`; console-command schedules need `server.schedule` and `server.console`; message schedules need only `server.schedule`. Updates can be created only for installed servers. Admins manage custom message templates from **Templates**. Deleting the server removes its schedules and run history.

## Current limits

SFTP has been tested with an in-process SSH/SFTP server and the panel's backup lifecycle has fake-store coverage. SMB has client configuration, fake-store create/verify/delete, and target-management coverage. Azure and GCS REST clients and target lifecycles have request-fixture coverage; no live Azure account, Google Cloud project, or browser acceptance was available. The S3 integration uses an in-repository REST client; run the gated emulator acceptance in `internal/backup/s3_test.go` by setting `DOCKLIGHT_S3_TEST_ENDPOINT`, `DOCKLIGHT_S3_TEST_BUCKET`, `DOCKLIGHT_S3_TEST_REGION`, `DOCKLIGHT_S3_TEST_ACCESS_KEY`, and `DOCKLIGHT_S3_TEST_SECRET_KEY`. A generic signed webhook can report backup and scheduled-action success or failure; see [notifications](notifications.md). Live browser acceptance for the new realm/global schedule management page is still pending.
