# Network address and reachability

The admin-only **Network** page stores an optional public hostname, such as `play.example.com`. Docklight removes an `http://` or `https://` scheme and a trailing slash. Enter the hostname only; the port comes from the server template and its allocated host-port mapping. Clearing this field uses the automatically detected public IP.

If no hostname is saved, Docklight calls `https://api.ipify.org?format=json` with a three-second timeout and caches a valid IP for one hour. When a refresh fails, it keeps the last successful address. The Network page shows both the detected value and effective host. Detection is initiated when a signed-in user opens that page or a server's reachability check runs; a detected address is not saved as a configuration value unless an administrator explicitly enters it.

Running and starting servers show **Online from outside** on their Overview tab. A declared Rune query protocol is probed at its allocated query/game port; otherwise Docklight attempts a TCP connection to the game port or first declared non-RCON port. The check has a four-second timeout and caches its result for 30 seconds. DNS results are resolved before connecting; loopback, unspecified, and multicast addresses are never probed.

This check runs from the Docklight host. Routers that do not support NAT loopback can report a false negative even while clients on the public internet can connect. A positive result confirms only that the tested protocol or TCP port responded from the panel host; it does not test every client network or guarantee a firewall permits every user.

## UPnP port forwarding

The **Router port forwarding** section uses UPnP Internet Gateway Device discovery on the host's IPv4 LAN. It reports the LAN address used by Docklight, the router's WAN address, the number of saved Docklight mappings, and servers with cleanup still pending. UPnP must be enabled on the router and the host must be able to discover it on the same LAN.

The UPnP and UniFi administrator switches are off by default. Each server's **Forward eligible ports automatically** preference is on by default, but has no effect until an administrator enables a router forwarding provider. Enabling a router provider applies mappings to currently running opted-in servers; newly started servers are mapped after Docker starts them. Nginx Proxy Manager uses its own master switch and per-server hostname, independent of this router preference.

Docklight forwards each declared game port using its allocated host port as both the external and internal port. TCP and UDP declarations are mapped separately. RCON, admin, management, and console ports are excluded. Mappings use a permanent router lease. If a router port already belongs to another rule, Docklight leaves it alone and reports the conflict.

Docklight saves the target and a unique `Docklight:` description for every rule it creates. On stop, confirmed container exit, explicit per-server opt-out, global opt-out, and deletion, Docklight checks the router's current protocol, ports, internal client, and description before deleting a saved rule. If the router is unavailable, it keeps cleanup records for a later attempt. Deleting a server is paused while its recorded mappings cannot be safely cleared, so the host ports are not released for another server while a stale router rule may remain.

UPnP mapping behavior is covered with fake-router tests. No physical router was available for discovery or host-level acceptance in this environment. A local reachability probe can still report a false negative when the router lacks NAT loopback.

## UniFi port forwarding

The **UniFi port forwarding** section connects directly to a local UniFi Network controller. Enter its URL, a local controller account, and a site name (usually `default`); save the settings and test the connection. The integration accepts a controller's self-signed HTTPS certificate. The username and password are encrypted with the panel secret, never returned by the settings API, and should use a dedicated account with only the rights needed to manage port-forward rules.

The global switch starts off. Each server uses the existing **Forward eligible ports automatically** preference. When enabled, Docklight clears old rules carrying that server's exact tag before starting it, then forwards declared game ports to the host's LAN address. RCON, admin, management, and console ports are excluded. Stop, confirmed container exit, per-server opt-out, and deletion remove only rules with that exact server tag. Other controller rules are left unchanged. If the controller cannot be reached during cleanup, server deletion is held until the rules can be checked and removed.

**Review rules** lists the controller's current port-forward rules. Docklight-tagged entries targeting this host's LAN address that cannot be matched to a local server are shown as strays; deleting them requires selecting the individual rules and confirming the action. Rules from other panels and Docklight rules targeting other hosts are not included in that delete action.

UniFi's local API documentation varies by Network version and is available in **Network > Integrations**. Docklight currently uses the controller's classic local login and site port-forward endpoints; the connection tests use a simulated controller. A real controller and its installed Network version still need acceptance testing against the [official local API guidance](https://help.ui.com/hc/en-us/articles/30076656117655-Getting-Started-with-the-Official-UniFi-API).

## Nginx Proxy Manager

The **Nginx Proxy Manager** section connects to a local NPM API URL, usually the admin port such as `http://192.168.1.20:81`. Enter an NPM account email and password, a base domain, and optionally the internal host Docklight should forward to. Passwords are encrypted at rest and never returned. NPM uses the connected account's profile email for Let's Encrypt; its API does not accept a separate contact address, so Docklight's optional contact field must match the account email or remain blank. If the internal host is blank, Docklight detects its LAN IPv4 address from the route to NPM. The **Test connection** button authenticates and reads the existing proxy-host list without changing it. Self-signed HTTPS certificates are accepted; redirects are refused.

The NPM master switch starts off. For each server, **Settings → Public web hostname** accepts a bare label (joined to the configured base domain), a full hostname, or blank to disable that server's proxy. A started server uses its declared TCP `web` port, falling back to its first declared TCP port, and the allocated host port. UDP-only servers are skipped. This hostname setting is separate from router forwarding.

Administrators can add more hostnames in that server's **Settings → Additional hostnames** card. Each entry is a full hostname and can target one declared TCP port; an empty target uses the same `web`-then-first-TCP selection. Docklight provisions an NPM host when the server is running. NPM does not change DNS, so the name must already resolve to the proxy. Stop, confirmed exit, and deletion remove Docklight's saved proxy host. If provider cleanup fails, the route remains marked for retry.

Docklight creates and records a proxy host with websocket support and common-exploit blocking enabled, then asks NPM to add a Let's Encrypt certificate and force SSL. If certificate creation fails, the saved host stays available without SSL and Docklight displays a warning. NPM first stores Docklight's ownership metadata on the plain host; it clears that metadata during certificate creation because NPM also passes proxy-host metadata into the certificate record, then restores the host marker afterward. NPM must be reachable from Docklight; public DNS must resolve to the proxy, and inbound HTTP on port 80 must reach NPM for the usual ACME HTTP challenge. Docklight does not change DNS records.

Each created host ID is recorded locally. Stop, confirmed container exit, hostname change, NPM settings changes, global disable, and server deletion remove the saved host. If NPM is unavailable during deletion or cleanup, Docklight keeps the server and cleanup record so the host can be removed safely later. Fake API tests cover authentication, ownership, lifecycle, fallback, and retry; this environment had no live NPM instance or public ACME path.

## Cloudflare Tunnel

The **Cloudflare Tunnel** section manages public HTTP routes through a remotely managed Cloudflare Tunnel. Create an API token with Tunnel edit permission on the account and DNS edit permission on the zone. Enter the token, account ID, tunnel ID, and base domain. The token is encrypted at rest and never returned. The zone ID is optional; when omitted, Docklight looks up the base domain in that account and caches the matching zone ID. **Test connection** reads the tunnel configuration and resolves the zone only when needed; it does not call Cloudflare's token-verification endpoint.

Each server's Settings page accepts a subdomain label, a full hostname inside the configured base domain, or blank to remove its route. When starting, Docklight sends the allocated TCP `web` port, or the first TCP port, through the configured internal host. Leave that field blank to use the host's LAN address selected by its route to Cloudflare. If a configured IP is no longer assigned to the Docklight host, Docklight falls back to the current LAN address and logs the change. Ensure the `cloudflared` connector can reach that host and port; its `TUNNEL_TOKEN` is the connector token, not the tunnel ID.

Administrators can also add full hostnames in the server's **Settings → Additional hostnames** card and select a declared TCP target port. Cloudflare routes must be inside the configured base domain. Docklight records the ingress service and exact DNS record ID for each extra route; a foreign ingress rule or DNS record is left untouched. Routes are provisioned for running servers and reconciled every ten minutes.

Docklight reads the existing ingress configuration, preserves unrelated rules and fields, places its route before the terminal `http_status:404` fallback, then creates or updates a proxied CNAME to `<tunnel-id>.cfargotunnel.com`. A CNAME that points to another tunnel, or a conflicting DNS record, is left untouched and shown as an error. If DNS cannot be changed after the ingress route is saved, the route remains and Docklight retries reconciliation every ten minutes. Stop, confirmed exit, hostname changes, settings changes, and deletion remove only the saved route and DNS records that still target the configured Tunnel. Deletion waits if cleanup cannot be completed safely.

The **Domains** page combines primary and additional Cloudflare/NPM hostnames for every server you can view. It shows whether Docklight has provisioned each provider and surfaces Cloudflare DNS conflicts or internal-target errors. The live check prefers HTTPS, retries a certificate-authority failure once with validation disabled and a visible warning, then tries HTTP when HTTPS does not respond. It never follows redirects, warns on 5xx responses, and caches results for 30 seconds. The dialer resolves the name at connection time, rejects private/local/link-local/reserved addresses, and connects directly to the checked public IP to prevent DNS rebinding. `GET /api/domains/cloudflare` still lists every hostname in the Tunnel configuration, including routes created outside Docklight. This build has not been accepted against a live Cloudflare account or public DNS zone.

## IP blocking

The admin **IP blocking** page manages single public IP addresses. When Cloudflare is configured, Docklight creates an IP Access Rule scoped to the selected zone. The token needs **Zone → Firewall Services → Edit**. The rule blocks HTTP/S requests proxied through that zone. If Cloudflare cannot create the rule, Docklight can use host nftables when its fallback switch is enabled. That backend drops locally delivered TCP 80 and 443 only; it does not affect game ports or SSH. Docker-published container traffic normally uses the `forward` chain and is outside this host-input fallback.

The feature is off by default. Docklight rejects private, local, Cloudflare, CGNAT/Tailscale, documentation, benchmarking, reserved, manually allowlisted, and recent administrator addresses. Rules can expire after up to one year. Reconciliation checks for external deletion or modification and cleans expired rules every minute. The API uses a zone ID, so these are not account-wide rules. Cloudflare recommends custom rules for IP-based filtering in general, while Docklight uses individually owned IP Access Rules to support safe per-address cleanup and expiry. See [Cloudflare's API documentation](https://developers.cloudflare.com/api/resources/firewall/subresources/access_rules/methods/create/).

Host nftables requires the systemd service to receive `CAP_NET_ADMIN`; see the [security guide](security.md#ip-blocking) for the override. Docklight owns only its marked `inet yggdrasil` table, chain, and sets, and refuses to change unmarked nftables objects. Cloudflare IPv4/IPv6 ranges and selected non-routable/special-use ranges from the [IANA IPv4](https://www.iana.org/assignments/iana-ipv4-special-registry) and [IANA IPv6](https://www.iana.org/assignments/iana-ipv6-special-registry) registries are embedded and should be refreshed when those sources change. Cloudflare's published [IPv4](https://www.cloudflare.com/ips-v4) and [IPv6](https://www.cloudflare.com/ips-v6) lists are also used.
