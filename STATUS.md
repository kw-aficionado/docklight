## Phase 2 backup, scheduling, and notification slices

Implemented encrypted local and remote backups for one configured S3-compatible, SFTP, or SMB destination, with a server **Backups** tab and scoped `server.backup` permission. Archives use authenticated AES-GCM chunks; all remote protocols stream the archive to storage and download it again to verify its checksum, encryption, and contents before recording it. The S3 client signs requests with SigV4 and uses multipart uploads for larger objects; SFTP uses password-authenticated SSH/SFTP and SMB uses SMB2 NTLMv2. Restore checks the saved checksum and encrypted archive, rejects symlinks and unsafe paths, and overlays archived files while preserving paths absent from the archive. Conflicting paths stop the restore and roll back prior writes. Retention uses database records and removes remote objects; server deletion cleans up recorded local and remote copies. The default retention is 10 per server, configurable from 1 to 100. Backups require a stopped server and use `auth.secret_key`; keep that key with the database and backup files. Remote target credentials and host or endpoint are encrypted and redacted. While remote backup records exist, the protocol, host, port, bucket or share, region, and prefix are locked; credentials can rotate. Backup schedules can write locally or to the enabled remote protocol selected when the schedule is created.

Schedules support per-server, realm, and global scopes with numeric five-field or six-field cron expressions in host-local time. Per-server actions require `server.schedule` plus `server.backup`, `server.control`, or `server.console` as applicable; message schedules need only `server.schedule`. Administrators create realm and global schedules from **Manage → Schedules** and can queue any schedule to run now. Realm membership is resolved at each firing, and the run history records one outcome per current target. The scheduler retains the latest 100 runs per schedule and returns the latest 50. Backup, start, stop, restart, update, console-command, and message actions work in all three scopes. A start requires an installed server, and duplicate starts or stops with no container are recorded as skipped. Updates stop each server, rerun its template installer against existing data when configured, pull the current image, and start a fresh container; scoped update runs wait for each server to return to running. A fleet update stops dispatching after three consecutive update failures; player-online skips do not count as failures. For a background restart countdown, a cron occurrence that becomes due before the previous run finishes is recorded as skipped and advanced to the next cron time. Console commands and snapshotted message template values are encrypted at rest and omitted from schedule and run-history responses. Restart warnings use template-configured countdown commands and run asynchronously; manual server changes cancel a countdown. Query-capable templates can skip a restart or update when players are online; unavailable counts are recorded and the action proceeds.

## Phase 2 private app-stack slice

Templates can define up to eight sidecars, including optional services controlled by a templated boolean and stateless workers without data mounts. Docklight creates a dedicated ownership-labeled bridge per server, starts enabled services before the main app, and gives each sidecar a private DNS alias. Sidecars with image-declared Docker health checks must become healthy within a shared two-minute window before the main app starts; services without a health check are not delayed. Sidecars have no host port bindings in this release. The main app mounts only its `_app` data directory; databases live in `_stack` outside its filesystem and Files tab. Backups archive the full server data root, including both. Stop and restart sequence containers as a unit; deletion removes sidecars and their network before deleting server data. CPU and memory ceilings are divided across the main app and sidecars instead of multiplying the configured server budget. Sidecar environment is isolated to that container, including decrypted secrets. The runtime monitor updates sidecar error state after confirmed exit/missing observations; generic Docker errors leave the last state unchanged. One-shot sidecar commands require `server.console`, run as the configured container user, limit command length and output, wait up to 30 seconds for completion, and redact template secrets; a timed-out command may continue in its container. Audit records omit command text and output.

The included WordPress + MariaDB template demonstrates the feature. ## Phase 3 IP blocking

The admin **IP blocking** page manages one public IPv4 or IPv6 address per rule. It prefers a zone-scoped Cloudflare IP Access Rule when the configured Cloudflare zone and API permission are available; optional host nftables is the fallback. Cloudflare blocks apply to proxied web traffic for that zone. Host rules drop only TCP 80 and 443 in the host's `input` chain, leaving SSH and game ports alone. Docker-published traffic normally traverses `forward`, so the host fallback does not intercept Docker-forwarded container traffic in this slice; use Cloudflare for proxied container web services. Host rules live in the Docklight-marked `inet yggdrasil` table; an existing unmarked table is never modified. Rule removal checks Docklight ownership before changing Cloudflare or nftables state. Rules can expire after a chosen interval or remain until removed.

Blocking is off by default. Administrators can maintain up to 256 protected IPs or CIDR ranges. Docklight also rejects private, local, link-local, Cloudflare, CGNAT/Tailscale, documentation, benchmark, and reserved ranges, plus addresses used by administrators in the last 30 days. Admin connection addresses are retained in SQLite for that 30-day safety window. The configured Cloudflare API token needs the zone-level **Firewall Services → Edit** permission. Host nftables requires the systemd service to have `CAP_NET_ADMIN`; the installer does not grant it. Cloudflare ranges are embedded from Cloudflare's published IPv4/IPv6 lists as of 2026-11-01; IANA special-use prefixes are also embedded. Update the protected-range lists when those sources change.

Startup and once-per-minute reconciliation repair managed Cloudflare and nftables rules and remove expired entries. The feature compiled and the browser script syntax checked in this checkout; no Cloudflare account, privileged host firewall, or end-to-end admin browser acceptance was available. The `off`/`propose`/`auto` setting is stored for the planned Kvasir workflow; only manual blocks are active in this slice.

Secrets are sent only in the per-pull `X-Registry-Auth` header and never written to the daemon login store or host credential files. Registry save and delete actions are audited.

Tests cover normalization, encrypted-at-rest storage, masked API responses, in-place replacement, admin-only listing, audit redaction, Docker auth-check behavior, per-pull credential isolation, and login-required error wording. The migration test covers schema 22. Docker-host pulls and visual browser review remain pending because this environment has no Docker daemon and the panel listener is blocked by the sandbox.

## Phase 2 password recovery

Administrators can set a unique account email. Public forgot-password requests accept a username or email and return one generic response, are rate limited by IP and identifier, and send asynchronously through the first enabled global SMTP email channel. Reset tokens are 256-bit random values; only their SHA-256 hashes are stored, they expire after one hour, and successful use atomically changes the password, revokes web sessions, consumes outstanding reset tokens, clears the username lockout, and records `user.password_reset`. TOTP remains enabled. `server.public_url` pins the reset-link origin; when unset the request origin is used. The UI removes the token query parameter immediately and responses set `Referrer-Policy: no-referrer`.

Tests cover identical responses for unknown accounts, accounts without email, and missing SMTP setup; recipient routing; configured-origin links; hash-only storage; token expiry and replay; session invalidation; audit history; and unique validated emails. Migration 24 adds the account email and reset-token table. SMTP transport is tested independently with an in-process protocol fixture; external mail delivery and live browser review remain pending.

## Phase 2 passkeys

Users can add, rename, and remove their own passkeys from Account. Passkey sign-in is discoverable and usernameless; registration and sign-in require user verification and a resident credential. Ceremony state stays server-side, is single-use, and expires after five minutes. The RP ID follows the request hostname, the origin honors `X-Forwarded-Proto`, and the browser must use HTTPS or localhost. Credential records are encrypted with the panel secret; names, added time, and last-used time are shown in the account panel. API, origin, timeout, storage, and rate-limit tests cover the server paths. A live authenticator/browser ceremony still needs device-level acceptance.

## Environment limits and remaining acceptance work

- Docker CLI and daemon are absent here. A Minecraft server install/start/ready/query/console/graceful-save cycle, Vaultwarden and Uptime Kuma browser access, and live WordPress + MariaDB behavior remain unverified. Stack lifecycle has deterministic fake-Engine coverage.
- This environment denies local TCP/UDP binds, so the network fixture tests are skipped by default. Set `YGGDRASIL_TEST_NETWORK=1` on a host that permits loopback binds to run them.
- The Backup storage, private-services overview, public status page, and catalog administration screens were syntax-checked and API-tested but not visually exercised in a live browser: this sandbox rejected the panel listener with `bind: operation not permitted`.
- `install.sh` syntax is checked but its package installation, systemd setup, and re-run preservation must be tested on a fresh Debian 12 or Ubuntu 24.04 VM.
- No release owner/repository is configured. The installer needs a source checkout, `YGG_BINARY_URL`, `YGG_BINARY_FILE`, or `YGG_REPO` until release artifacts are published.
- No MinIO or other S3-compatible emulator is available here. The S3 path has deterministic fake-store and signed-request coverage, but credential policy and provider interoperability still need the gated live-object test.
- The Docklight UI and Backups tab were browser-smoke-tested at the default desktop viewport. Mobile breakpoints still need a separate browser pass.

Before calling Phase 1 accepted, run the Docker and installer acceptance steps from the user brief on a disposable Debian/Ubuntu host and verify the embedded UI in a browser.
