## Phase 2 backup, scheduling, and notification slices

Implemented encrypted local and S3-compatible backups with a server **Backups** tab and scoped `server.backup` permission. Archives use authenticated AES-GCM chunks; the S3 client signs requests with SigV4, streams uploads, uses multipart for larger objects, rejects redirects, and verifies the remote copy before recording it. Restore checks the saved checksum and encrypted archive, rejects symlinks and unsafe paths, and overlays archived files while preserving files absent from the archive. Conflicting paths stop the restore and roll back prior writes. Retention is based on database records and removes remote objects; server deletion cleans up recorded local and S3 copies. The default retention is 10 per server, configurable from 1 to 100. Backups require a stopped server and use `auth.secret_key`; keep that key with the database and backup files. S3 target credentials are encrypted and redacted, and the target's endpoint/bucket/region/prefix are locked while S3 records exist. Backup schedules can write locally or to the enabled S3 target selected when the schedule is created.

Per-server schedules accept numeric five-field or six-field cron expressions in host-local time. Backup schedules require `server.schedule` plus `server.backup`; start, stop, and restart schedules require `server.schedule` plus `server.control`; console-command schedules require `server.schedule` plus `server.console`; message schedules require only `server.schedule` and are available on Minecraft Java and Bedrock. A start requires an installed server, and duplicate starts or stops with no container are recorded as skipped. Console commands are single-line, encrypted at rest, and sent only while the server is running. Message schedules render one of five built-in or admin-managed custom Minecraft command templates with `server_name`, `minutes`, and `seconds`, then encrypt the selected template snapshot and values. Message text is not returned in schedule or run-history responses. Restart warnings use template-configured countdown commands and run asynchronously; manual server changes cancel a countdown. Query-capable templates can skip a restart when players are online; unavailable counts are recorded and the restart proceeds. Schedule history, enable/disable, and next-run tracking are shared across all six actions.

The API tests cover permission boundaries, cross-server denial, encryption at rest, creation, verification, restore, automatic/manual retention, corruption detection, and deletion. S3 tests cover the official SigV4 example, path-style requests, streaming upload, multipart completion, redirect rejection, target redaction and identity locking, and a fake-store create/verify/restore/prune/delete lifecycle. Bypassing remote verification made the corruption case fail with an incorrectly accepted `201`; restoring the verification guard made it pass. For scheduled S3 backups, a planted dispatch regression that forced local storage failed the destination test; restoring the stored destination made it pass. A real S3-compatible emulator test is gated by `DOCKLIGHT_S3_TEST_ENDPOINT`, `DOCKLIGHT_S3_TEST_BUCKET`, `DOCKLIGHT_S3_TEST_REGION`, `DOCKLIGHT_S3_TEST_ACCESS_KEY`, and `DOCKLIGHT_S3_TEST_SECRET_KEY`; it has not run in this environment. Schedule tests cover cron parsing, action permissions, encrypted console-command and message-template storage/dispatch, API redaction, selected S3 destination dispatch and failure recording when S3 is disabled, backup worker outcomes, start/stop dispatch and skipped outcomes, restart countdown ordering/cancellation, online-player skipping, query-failure continuation, background execution, and run history. Template tests cover all six built-ins, app-stack validation, secret interpolation, admin-only custom CRUD, placeholder validation, and built-in protection. Notification tests cover admin-only access, encrypted storage, HMAC signatures, webhook delivery, scheduled outcome events with run-detail redaction, and redirect rejection. Loopback browser smokes loaded the per-server restart options, saved a restart with a one-minute warning and a 2027 next run, confirmed it in the list, showed the player-count checkbox for Minecraft Java, opened the encrypted console-command form, rendered the message schedule inputs, and saved the scheduled-action notification choices. Docker lifecycle and console execution remain unverified against a live game server in this environment. SFTP, SMB, other scheduler actions, and realm/global scheduling remain unimplemented.

An administrator can configure one signed outgoing webhook for backup, scheduler, crash, watchdog, and low-disk events, send a test event, and choose which events to receive. Scheduler event payloads include the schedule ID, action, and outcome, but omit run details. Skipped schedule actions do not notify. The URL and optional HMAC signing key are encrypted with `auth.secret_key`; responses reveal only whether each is configured. Redirects are not followed; HTTPS is required except localhost loopback testing. Discord, Telegram, SMTP, retries, and delivery history remain unimplemented.

Runtime monitoring records confirmed container exits and repeatedly confirmed missing containers for servers Docklight marked as running. It waits 60 seconds after panel startup, requires a healthy Docker ping, and confirms the same stopped/missing observation at least 15 seconds later. Unknown Docker errors leave the last known server state unchanged. Confirmed incidents set the server to **Needs attention**, preserve server data, and appear in the per-server **History** tab. The latest 50 incidents are shown and 100 retained. Administrators can opt into a signed `server.crash` webhook with the server name and incident details. Runtime tests cover startup grace, Docker outages, exit/missing confirmation, RBAC, startup exits, deletion cleanup, data preservation, and webhook delivery. Planted faults bypassing debounce or changing the webhook event name caused the corresponding tests to fail. Browser verification used seeded incident data; Docker Engine was unavailable for a live crash test. Query-based automatic recovery is documented separately below and still needs Docker-host acceptance.

Low-disk monitoring checks the filesystem containing Docklight's data directory every five minutes. It sends the opt-in `host.disk_low` webhook below 10% free and rearms at 15%; its message reports capacity and names server-data and local-backup paths. The admin Notifications page reports current capacity and alert state. Tests cover threshold edges, repeat suppression, rearming, persistence, and webhook delivery. A planted inclusive-boundary fault made the threshold test fail at exactly 10%; after restoring the strict threshold it passed. Other mounted filesystems are not enumerated, and no files are automatically deleted.

Automatic recovery is opt-in per server and limited to templates with player-query support. The watchdog probes every 20 seconds with a 3-second timeout, requires three consecutive failures, and applies a four-minute cooldown after each recovery attempt. It retries a failed restart up to three times with 15-second spacing. Cooldowns and successful heals are persisted so a panel restart does not reset the 30-minute quarantine window. Five successful recoveries within 30 minutes put the server in quarantine; manual start or stop clears the quarantine. The specification appendix uses both “more than five” and “five” as its threshold; this implementation quarantines after the fifth successful recovery. Deterministic tests cover startup grace, Docker unavailability, the failure threshold, healthy-probe reset, cooldown across monitor-state reloads, retries and manual cancellation, webhook delivery, access checks, query-protocol eligibility, and quarantine while a new start is still progressing. No live Docker engine was available for restart acceptance.

The UI assets are embedded and have no CDN or frontend package dependency. It is a compact HTML/CSS/JavaScript app rather than the specified Svelte/Tailwind build. It has light and dark themes, but no offline service worker or complete installable PWA.

The template and config readers intentionally accept a bounded subset of YAML rather than general YAML 1.2. Unknown template fields are ignored. JWT signing and WebSocket framing are implemented locally because the corresponding requested dependencies were unavailable offline. These substitutions are recorded in [DECISIONS.md](DECISIONS.md).

## Phase 2 private app-stack slice

Templates can define up to eight sidecars, including optional services controlled by a templated boolean and stateless workers without data mounts. Docklight creates a dedicated ownership-labeled bridge per server, starts enabled services before the main app, and gives each sidecar a private DNS alias. Sidecars with image-declared Docker health checks must become healthy within a shared two-minute window before the main app starts; services without a health check are not delayed. Sidecars have no host port bindings in this release. The main app mounts only its `_app` data directory; databases live in `_stack` outside its filesystem and Files tab. Backups archive the full server data root, including both. Stop and restart sequence containers as a unit; deletion removes sidecars and their network before deleting server data. CPU and memory ceilings are divided across the main app and sidecars instead of multiplying the configured server budget. Sidecar environment is isolated to that container, including decrypted secrets. The runtime monitor updates sidecar error state after confirmed exit/missing observations; generic Docker errors leave the last state unchanged. One-shot sidecar commands require `server.console`, run as the configured container user, limit command length and output, wait up to 30 seconds for completion, and redact template secrets; a timed-out command may continue in its container. Audit records omit command text and output.

The included WordPress + MariaDB template demonstrates the feature. Fake Docker Engine tests cover private-network membership, DNS alias, persistent bind, secret isolation, unexposed sidecar ports, shared limits, optional/stateless services, start/stop order, status recovery, deletion, and rollback after main-container start failure. A backup/restore check confirms two files from `_app` and `_stack` return with their contents. A planted regression that mounted the full data root made the isolation test fail; restoring the `_app` mount made it pass. Private-service logs stream in the overview for users with `server.view`; one-shot commands require `server.console` and both operations verify Docker ownership and redact template secrets. Fake Docker Engine tests cover command dispatch, stopped-service rejection, permission enforcement, output redaction, and audit redaction. A planted redaction bypass made the command test fail; restoring secret redaction made it pass. Docker-host acceptance and visual browser review of the private-services overview remain pending.

## Phase 3 public status page slice

The administrator can configure a public Docklight status page with a master switch and per-server opt-ins. It is disabled by default; all public routes return `404` while disabled. The JSON summary contains only selected server names, template names, normalized availability, and player counts sampled by successful authenticated panel queries within the last 15 minutes. It omits IDs, ports, addresses, and configuration. JSON is cached for 15 seconds, setting and sample changes clear the cache, and the branded page refreshes every 30 seconds with `noindex` metadata.

Tests cover default-off routing, admin-only settings, the two opt-in gates, title/selection validation and rollback, online/starting/uninstalled state mapping, stale-player omission, public-field redaction, cache headers and invalidation, and page/script serving. Removing the per-server opt-in filter made the test expose the private server; restoring the filter made it pass. Live-browser visual acceptance remains pending because this sandbox blocks the panel listener.

- This environment denies local TCP/UDP binds, so the network fixture tests are skipped by default. Set `YGGDRASIL_TEST_NETWORK=1` on a host that permits loopback binds to run them.
- The new Backup storage, private-services overview, and public status-page screens were syntax-checked and API-tested but not visually exercised in a live browser: this sandbox rejected the panel listener with `bind: operation not permitted`.
- `install.sh` syntax is checked but its package installation, systemd setup, and re-run preservation must be tested on a fresh Debian 12 or Ubuntu 24.04 VM.
- No release owner/repository is configured. The installer needs a source checkout, `YGG_BINARY_URL`, `YGG_BINARY_FILE`, or `YGG_REPO` until release artifacts are published.
- No MinIO or other S3-compatible emulator is available here. The S3 path has deterministic fake-store and signed-request coverage, but credential policy and provider interoperability still need the gated live-object test.
- The Docklight UI and Backups tab were browser-smoke-tested at the default desktop viewport. Mobile breakpoints still need a separate browser pass.
