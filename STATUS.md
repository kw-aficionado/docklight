## Phase 2 backup, scheduling, and notification slices

Implemented encrypted local and remote backups for one configured S3-compatible, SFTP, or SMB destination, with a server **Backups** tab and scoped `server.backup` permission. Archives use authenticated AES-GCM chunks; all remote protocols stream the archive to storage and download it again to verify its checksum, encryption, and contents before recording it. The S3 client signs requests with SigV4 and uses multipart uploads for larger objects; SFTP uses password-authenticated SSH/SFTP and SMB uses SMB2 NTLMv2. Restore checks the saved checksum and encrypted archive, rejects symlinks and unsafe paths, and overlays archived files while preserving paths absent from the archive. Conflicting paths stop the restore and roll back prior writes. Retention uses database records and removes remote objects; server deletion cleans up recorded local and remote copies. The default retention is 10 per server, configurable from 1 to 100. Backups require a stopped server and use `auth.secret_key`; keep that key with the database and backup files. Remote target credentials and host or endpoint are encrypted and redacted. While remote backup records exist, the protocol, host, port, bucket or share, region, and prefix are locked; credentials can rotate. Backup schedules can write locally or to the enabled remote protocol selected when the schedule is created.

Per-server schedules accept numeric five-field or six-field cron expressions in host-local time. Backup schedules require `server.schedule` plus `server.backup`; start, stop, and restart schedules require `server.schedule` plus `server.control`; console-command schedules require `server.schedule` plus `server.console`; message schedules require only `server.schedule` and are available on Minecraft Java and Bedrock. A start requires an installed server, and duplicate starts or stops with no container are recorded as skipped. Console commands are single-line, encrypted at rest, and sent only while the server is running. Message schedules render one of five built-in or admin-managed custom Minecraft command templates with `server_name`, `minutes`, and `seconds`, then encrypt the selected template snapshot and values. Message text is not returned in schedule or run-history responses. Restart warnings use template-configured countdown commands and run asynchronously; manual server changes cancel a countdown. Query-capable templates can skip a restart when players are online; unavailable counts are recorded and the restart proceeds. Schedule history, enable/disable, and next-run tracking are shared across all six actions.

The API tests cover permission boundaries, cross-server denial, encryption at rest, creation, verification, restore, automatic/manual retention, corruption detection, and deletion. S3 tests cover the official SigV4 example, path-style requests, streaming upload, multipart completion, redirect rejection, target redaction and identity locking, and a fake-store create/verify/restore/prune/delete lifecycle. Bypassing remote verification made the corruption case fail with an incorrectly accepted `201`; restoring the verification guard made it pass. For scheduled S3 backups, a planted dispatch regression that forced local storage failed the destination test; restoring the stored destination made it pass. A real S3-compatible emulator test is gated by `DOCKLIGHT_S3_TEST_ENDPOINT`, `DOCKLIGHT_S3_TEST_BUCKET`, `DOCKLIGHT_S3_TEST_REGION`, `DOCKLIGHT_S3_TEST_ACCESS_KEY`, and `DOCKLIGHT_S3_TEST_SECRET_KEY`; it has not run in this environment. Schedule tests cover cron parsing, action permissions, encrypted console-command and message-template storage/dispatch, API redaction, selected S3 destination dispatch and failure recording when S3 is disabled, backup worker outcomes, start/stop dispatch and skipped outcomes, restart countdown ordering/cancellation, online-player skipping, query-failure continuation, background execution, and run history. Template tests cover all six built-ins, app-stack validation, secret interpolation, admin-only custom CRUD, placeholder validation, and built-in protection. Notification tests cover admin-only access, encrypted storage, HMAC signatures, webhook delivery, scheduled outcome events with run-detail redaction, and redirect rejection. Loopback browser smokes loaded the per-server restart options, saved a restart with a one-minute warning and a 2027 next run, confirmed it in the list, showed the player-count checkbox for Minecraft Java, opened the encrypted console-command form, rendered the message schedule inputs, and saved the scheduled-action notification choices. Docker lifecycle and console execution remain unverified against a live game server in this environment. SFTP client tests use an in-process SSH/SFTP server over a buffered `net.Pipe` to exercise password authentication, upload, download, and delete. Panel tests cover SFTP credential encryption/redaction, fake-store create/verify/restore/delete, SFTP schedule selection, SMB configuration validation and fake-store create/verify/delete, target identity locking, and protocol switching after remote records are removed. Separate live SFTP and SMB hosts were not available for acceptance.

An administrator can configure the original signed webhook and multiple Discord, Telegram, JSON webhook, and SMTP email channels. New channels can be global or scoped to one server; configuration is encrypted with `auth.secret_key` and omitted from responses. Discord, Telegram, and webhook sends use HTTPS without redirects. Remote SMTP requires STARTTLS or implicit TLS; auth follows TLS. Delivery is asynchronous with fixed timeouts, no retries, and no delivery-history table. The legacy webhook supports per-event filters; new channels receive all supported events in their scope.

Channel tests cover encrypted configuration, response masking, admin routes, Discord/Telegram request formats, per-server delivery routing, SMTP validation and a `net.Pipe` mail exchange, and delete auditing. Live service credentials and browser review remain pending.

Runtime monitoring records confirmed container exits and repeatedly confirmed missing containers for servers Docklight marked as running. It waits 60 seconds after panel startup, requires a healthy Docker ping, and confirms the same stopped/missing observation at least 15 seconds later. Unknown Docker errors leave the last known server state unchanged. Confirmed incidents set the server to **Needs attention**, preserve server data, and appear in the per-server **History** tab. The latest 50 incidents are shown and 100 retained. Administrators can opt into a signed `server.crash` webhook with the server name and incident details. Runtime tests cover startup grace, Docker outages, exit/missing confirmation, RBAC, startup exits, deletion cleanup, data preservation, and webhook delivery. Planted faults bypassing debounce or changing the webhook event name caused the corresponding tests to fail. Browser verification used seeded incident data; Docker Engine was unavailable for a live crash test. Query-based automatic recovery is documented separately below and still needs Docker-host acceptance.

Low-disk monitoring checks the filesystem containing Docklight's data directory every five minutes. It sends the opt-in `host.disk_low` webhook below 10% free and rearms at 15%; its message reports capacity and names server-data and local-backup paths. The admin Notifications page reports current capacity and alert state. Tests cover threshold edges, repeat suppression, rearming, persistence, and webhook delivery. A planted inclusive-boundary fault made the threshold test fail at exactly 10%; after restoring the strict threshold it passed. Other mounted filesystems are not enumerated, and no files are automatically deleted.

Automatic recovery is opt-in per server and limited to templates with player-query support. The watchdog probes every 20 seconds with a 3-second timeout, requires three consecutive failures, and applies a four-minute cooldown after each recovery attempt. It retries a failed restart up to three times with 15-second spacing. Cooldowns and successful heals are persisted so a panel restart does not reset the 30-minute quarantine window. Five successful recoveries within 30 minutes put the server in quarantine; manual start or stop clears the quarantine. The specification appendix uses both “more than five” and “five” as its threshold; this implementation quarantines after the fifth successful recovery. Deterministic tests cover startup grace, Docker unavailability, the failure threshold, healthy-probe reset, cooldown across monitor-state reloads, retries and manual cancellation, webhook delivery, access checks, query-protocol eligibility, and quarantine while a new start is still progressing. No live Docker engine was available for restart acceptance.

The UI assets are embedded and have no CDN or frontend package dependency. It is a compact HTML/CSS/JavaScript app rather than the specified Svelte/Tailwind build. It has light and dark themes, but no offline service worker or complete installable PWA.

The template and config readers intentionally accept a bounded subset of YAML rather than general YAML 1.2. Unknown template fields are ignored. JWT signing and WebSocket framing are implemented locally because the corresponding requested dependencies were unavailable offline. These substitutions are recorded in [DECISIONS.md](DECISIONS.md).

## Phase 2 private app-stack slice

Templates can define up to eight sidecars, including optional services controlled by a templated boolean and stateless workers without data mounts. Docklight creates a dedicated ownership-labeled bridge per server, starts enabled services before the main app, and gives each sidecar a private DNS alias. Sidecars with image-declared Docker health checks must become healthy within a shared two-minute window before the main app starts; services without a health check are not delayed. Sidecars have no host port bindings in this release. The main app mounts only its `_app` data directory; databases live in `_stack` outside its filesystem and Files tab. Backups archive the full server data root, including both. Stop and restart sequence containers as a unit; deletion removes sidecars and their network before deleting server data. CPU and memory ceilings are divided across the main app and sidecars instead of multiplying the configured server budget. Sidecar environment is isolated to that container, including decrypted secrets. The runtime monitor updates sidecar error state after confirmed exit/missing observations; generic Docker errors leave the last state unchanged. One-shot sidecar commands require `server.console`, run as the configured container user, limit command length and output, wait up to 30 seconds for completion, and redact template secrets; a timed-out command may continue in its container. Audit records omit command text and output.

The included WordPress + MariaDB template demonstrates the feature. Fake Docker Engine tests cover private-network membership, DNS alias, persistent bind, secret isolation, unexposed sidecar ports, shared limits, optional/stateless services, start/stop order, status recovery, deletion, and rollback after main-container start failure. A backup/restore check confirms two files from `_app` and `_stack` return with their contents. A planted regression that mounted the full data root made the isolation test fail; restoring the `_app` mount made it pass. Private-service logs stream in the overview for users with `server.view`; one-shot commands require `server.console` and both operations verify Docker ownership and redact template secrets. Fake Docker Engine tests cover command dispatch, stopped-service rejection, permission enforcement, output redaction, and audit redaction. A planted redaction bypass made the command test fail; restoring secret redaction made it pass. Docker-host acceptance and visual browser review of the private-services overview remain pending.

## Phase 3 public status page slice

The administrator can configure a public Docklight status page with a master switch and per-server opt-ins. It is disabled by default; all public routes return `404` while disabled. The JSON summary contains only selected server names, template names, normalized availability, and player counts sampled by successful authenticated panel queries within the last 15 minutes. It omits IDs, ports, addresses, and configuration. JSON is cached for 15 seconds, setting and sample changes clear the cache, and the branded page refreshes every 30 seconds with `noindex` metadata.

Tests cover default-off routing, admin-only settings, the two opt-in gates, title/selection validation and rollback, online/starting/uninstalled state mapping, stale-player omission, public-field redaction, cache headers and invalidation, and page/script serving. Removing the per-server opt-in filter made the test expose the private server; restoring the filter made it pass. ## Phase 2 catalog repositories

The admin Templates page can save, browse, install, and remove GitHub, Gitea, and Forgejo catalogs. Saved credentials are encrypted and masked; repo tokens stay bound to their saved host/repository, while the optional panel-wide GitHub token is sent only to GitHub's API. Catalog traffic uses HTTPS, rejects redirects, bounds response and YAML sizes, caches successful directory listings for ten minutes, and exposes at most one subfolder level. Installing an existing community ID updates its YAML; built-in IDs are protected. Installed sources retain host, repository, path, and ref, and the manual update check reports missing or unreachable sources without applying changes automatically. No remote catalog is preconfigured; an administrator adds trusted repositories.

Catalog tests cover encrypted/masked/cleared tokens, GitHub-token isolation, redirect stopping, HTTPS repository validation, listing cache and depth, 512 KiB file limits, built-in protection, existing-ID updates, source provenance, manual version comparison, and source removal. The migration test covers schema 21. The live administration UI still needs browser review, and live GitHub/Gitea interoperability depends on external repositories and credentials.

## Phase 2 private registry credentials

Admins can save one encrypted username/secret pair per normalized registry, test it through Docker Engine, replace it by saving again, and remove it. Docker Hub aliases normalize to `docker.io`; image matching follows Docker's explicit-registry split rules and keeps credentials scoped to one host and port. Runtime images, stack sidecars, install images, and the helper image all use the same pull helper. Secrets are sent only in the per-pull `X-Registry-Auth` header and never written to the daemon login store or host credential files. Registry save and delete actions are audited.

Tests cover normalization, encrypted-at-rest storage, masked API responses, in-place replacement, admin-only listing, audit redaction, Docker auth-check behavior, per-pull credential isolation, and login-required error wording. The migration test covers schema 22. Docker-host pulls and visual browser review remain pending because this environment has no Docker daemon and the panel listener is blocked by the sandbox.

## Phase 2 password recovery

Administrators can set a unique account email. Public forgot-password requests accept a username or email and return one generic response, are rate limited by IP and identifier, and send asynchronously through the first enabled global SMTP email channel. Reset tokens are 256-bit random values; only their SHA-256 hashes are stored, they expire after one hour, and successful use atomically changes the password, revokes web sessions, consumes outstanding reset tokens, clears the username lockout, and records `user.password_reset`. TOTP remains enabled. `server.public_url` pins the reset-link origin; when unset the request origin is used. The UI removes the token query parameter immediately and responses set `Referrer-Policy: no-referrer`.

Tests cover identical responses for unknown accounts, accounts without email, and missing SMTP setup; recipient routing; configured-origin links; hash-only storage; token expiry and replay; session invalidation; audit history; and unique validated emails. Migration 24 adds the account email and reset-token table. SMTP transport is tested independently with an in-process protocol fixture; external mail delivery and live browser review remain pending.
