## Phase 2 backup, scheduling, and notification slices

Implemented local and remote backups for one configured S3-compatible, Google Cloud Storage, Azure Blob, SFTP, SMB, rclone, or Proxmox Backup Server destination, with a server **Backups** tab and scoped `server.backup` permission. Local and object-store archives use authenticated AES-GCM chunks; object-store protocols download the saved archive and verify its checksum, encryption, and contents before recording it. PBS instead sends a `.pxar` directly to the content-addressed datastore for chunk deduplication, with no Docklight-side archive encryption or download. The S3 client signs requests with SigV4 and uses multipart uploads for larger objects; GCS uses the native JSON API, service-account OAuth, and 16 MiB resumable chunks up to 5 TiB; Azure uses Shared Key or SAS authentication and streams block blobs in 16 MiB chunks, with an 800 GB object limit; SFTP uses password-authenticated SSH/SFTP with an administrator-verified SHA-256 host-key pin checked before password authentication; SMB uses SMB2 NTLMv2; rclone uses a pinned helper image and encrypted provider configuration; PBS uses a pinned, amd64 Proxmox client helper. Restore checks object-store checksums and archive structure, rejects unsafe paths, and overlays files while preserving paths absent from the archive. PBS restore is staged and rejects symlinks and special files before the overlay. Conflicting paths stop the restore and roll back prior writes. Object-store retention uses database records; PBS applies `--keep-last` and `--keep-daily` in each server group and removes stale panel rows after listing. Server deletion cleans up recorded local and remote copies. The default retention is 10 per server, configurable from 1 to 100. Backups require a stopped server. Object-store encryption uses `auth.secret_key`; PBS credentials are encrypted and redacted, while PBS data security and verification are managed by the PBS server. Backup schedules can write locally or to the enabled remote protocol selected when the schedule is created.

Rclone adds Jottacloud, Dropbox, OneDrive, Google Drive, Box, pCloud, MEGA, WebDAV, and custom config targets through a pinned helper; provider tokens refresh into encrypted target storage. PBS targets use port 8007 by default, optional SHA-256 certificate fingerprint pinning, a user and API token each granted `DatastorePowerUser`, per-server groups, staged restore, and PBS-side verification. Its helper image is built from Proxmox's static client package in `deploy/pbs-client/`, with `docker.pbs_client_image` as the override; the default GHCR tag has not been published from this checkout, so publish it or point the setting at a compatible image before using PBS. Go tests cover encrypted/redacted targets, rclone config/token handling, PBS repository syntax, target identity locking, snapshot IDs, and the existing backup and Docker attach paths. `go vet ./...`, `go test -count=1 ./...`, all six Node UI tests, and static Linux amd64/arm64 builds pass. Generated website files are current. This rclone/PBS slice has not had a live cloud, PBS, or Docker acceptance run.

Azure target settings use migration 52 without changing existing target rows. Account keys or SAS tokens are encrypted at rest and redacted; changing account identity, container, endpoint, or prefix is blocked while Azure backup records remain. The client, container-list and read/write/delete connectivity check, migration, schedule destination, and restore path have automated request and fake-store coverage. No live Azure account or browser acceptance was available.

GCS uses the existing target schema and encrypts the full service-account JSON key with `auth.secret_key`; OAuth access tokens remain memory-only. It calls the native Cloud Storage JSON API, rejects redirects, restricts resumable upload URLs to Google HTTPS hosts, streams unknown-length archives in 16 MiB chunks, checks acknowledged byte ranges, cancels incomplete sessions, and caps objects at 5 TiB. The bucket must already exist. Target listing, OAuth JWT signing, resumable upload, object read/delete, target redaction, schedule selection, and fake-store backup lifecycle have automated request-fixture coverage. No live Google Cloud project or browser acceptance was available.

Schedules support per-server, realm, and global scopes with numeric five-field or six-field cron expressions in host-local time. Per-server actions require `server.schedule` plus `server.backup`, `server.control`, or `server.console` as applicable; message schedules need only `server.schedule`. Administrators create realm and global schedules from **Manage → Schedules** and can queue any schedule to run now. Realm membership is resolved at each firing, and the run history records one outcome per current target. The scheduler retains the latest 100 runs per schedule and returns the latest 50. Backup, start, stop, restart, update, console-command, and message actions work in all three scopes. A start requires an installed server, and duplicate starts or stops with no container are recorded as skipped. For a Rune with an `update` block, a scheduled update runs that app script synchronously and skips stopped servers; otherwise, it reruns the template installer against existing data when configured, pulls the current image, and starts a fresh container. Scoped update runs wait for each server to return to running. A fleet update stops dispatching after three consecutive update failures; player-online skips do not count as failures. For a background restart countdown, a cron occurrence that becomes due before the previous run finishes is recorded as skipped and advanced to the next cron time. Console commands and snapshotted message template values are encrypted at rest and omitted from schedule and run-history responses. Restart warnings use template-configured countdown commands and run asynchronously; manual server changes cancel a countdown. Query-capable templates can skip a restart or update when players are online; unavailable counts are recorded and the action proceeds.

## Phase 2 private app-stack slice

Templates can define up to eight sidecars, including optional services controlled by a templated boolean and stateless workers without data mounts. Docklight creates a dedicated ownership-labeled bridge per server, starts enabled services before the main app, and gives each sidecar a private DNS alias. Sidecars with image-declared Docker health checks must become healthy within a shared two-minute window before the main app starts; services without a health check are not delayed. Sidecars have no host port bindings in this release. The main app mounts only its `_app` data directory; databases live in `_stack` outside its filesystem and Files tab. Backups archive the full server data root, including both. Stop and restart sequence containers as a unit; deletion removes sidecars and their network before deleting server data. CPU and memory ceilings are divided across the main app and sidecars instead of multiplying the configured server budget. Sidecar environment is isolated to that container, including decrypted secrets. The runtime monitor updates sidecar error state after confirmed exit/missing observations; generic Docker errors leave the last state unchanged. One-shot sidecar commands require `server.console`, run as the configured container user, limit command length and output, wait up to 30 seconds for completion, and redact template secrets; a timed-out command may continue in its container. Audit records omit command text and output.

The included WordPress + MariaDB template demonstrates the feature. Fake Docker Engine tests cover private-network membership, DNS alias, persistent binds (including multiple sidecar paths), secret isolation, unexposed sidecar ports, shared limits, optional/stateless services, start/stop order, status recovery, deletion, and rollback after main-container start failure. A backup/restore check confirms two files from `_app` and `_stack` return with their contents. A planted regression that mounted the full data root made the isolation test fail; restoring the `_app` mount made it pass. Private-service logs stream in the overview for users with `server.view`; one-shot commands require `server.console` and both operations verify Docker ownership and redact template secrets. Fake Docker Engine tests cover command dispatch, stopped-service rejection, permission enforcement, output redaction, and audit redaction. A planted redaction bypass made the command test fail; restoring secret redaction made it pass. Docker-host acceptance and visual browser review of the private-services overview remain pending.

## Phase 3 IP blocking

The admin **IP blocking** page manages one public IPv4 or IPv6 address per rule. It prefers a zone-scoped Cloudflare IP Access Rule when the configured Cloudflare zone and API permission are available; optional host nftables is the fallback. Cloudflare blocks apply to proxied web traffic for that zone. Host rules drop only TCP 80 and 443 in the host's `input` chain, leaving SSH and game ports alone. Docker-published traffic normally traverses `forward`, so the host fallback does not intercept Docker-forwarded container traffic in this slice; use Cloudflare for proxied container web services. Host rules live in the Docklight-marked `inet yggdrasil` table; an existing unmarked table is never modified. Rule removal checks Docklight ownership before changing Cloudflare or nftables state. Rules can expire after a chosen interval or remain until removed.

Blocking is off by default. Administrators can maintain up to 256 protected IPs or CIDR ranges. Docklight also rejects private, local, link-local, Cloudflare, CGNAT/Tailscale, documentation, benchmark, and reserved ranges, plus addresses used by administrators in the last 30 days. Admin connection addresses are retained in SQLite for that 30-day safety window. The configured Cloudflare API token needs the zone-level **Firewall Services → Edit** permission. Host nftables requires the systemd service to have `CAP_NET_ADMIN`; the installer does not grant it. Cloudflare ranges are embedded from Cloudflare's published IPv4/IPv6 lists as of 2026-11-01; IANA special-use prefixes are also embedded. Update the protected-range lists when those sources change.

Startup and once-per-minute reconciliation repair managed Cloudflare and nftables rules and remove expired entries. The feature compiled and the browser script syntax checked in this checkout; no Cloudflare account, privileged host firewall, or end-to-end admin browser acceptance was available. The `off`/`propose`/`auto` setting is reserved for future Assistant workflows; only manual blocks are active in this slice.

## Phase 3 disclosed usage beacon

## Phase 3 panel self-update

The admin Panel updates screen checks the configured GitHub repository for the latest stable `vX.Y.Z` release, shows current/update state and the last helper status, and provides manual release checks and queueing. A release build embeds its owner/repository; the installer can also set `YGG_REPO` or detect the GitHub origin for a source checkout. The sandboxed panel writes only a validated tag request into `/var/lib/yggdrasil/.update-request`; an independent root systemd path unit starts the oneshot helper. The helper accepts only strictly newer stable tags, downloads the architecture-matched official GitHub release asset and `SHA256SUMS` over HTTPS, verifies SHA-256 and `--version`, saves a rollback binary, installs, restarts, and records an atomic status file. Restart failure attempts rollback and reports whether service health was recovered.
