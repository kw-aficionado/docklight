## Phase 2 backup, scheduling, and notification slices

Implemented local encrypted backups with a server **Backups** tab and scoped `server.backup` permission. The stream is compressed and encrypted with authenticated AES-GCM chunks; files are checksummed and verified before registration. Restore verifies before staging, rejects symlinks and unsafe archive paths, then swaps the full data directory. The default retention is 10 per server, configurable from 1 to 100. Backups require a stopped server and use `auth.secret_key`; keep that key with the database and backup files. Server deletion removes its local backups.

Per-server schedules accept numeric five-field or six-field cron expressions in host-local time. Backup schedules require `server.schedule` plus `server.backup`; start, stop, and restart schedules require `server.schedule` plus `server.control`; console-command schedules require `server.schedule` plus `server.console`. A start requires an installed server, and duplicate starts or stops with no container are recorded as skipped. Console commands are single-line, encrypted at rest, and sent only while the server is running. Restart warnings use template-configured countdown commands and run asynchronously; manual server changes cancel a countdown. Query-capable templates can skip a restart when players are online; unavailable counts are recorded and the restart proceeds. Schedule history, enable/disable, and next-run tracking are shared across all five actions.

The API tests cover permission boundaries, cross-server denial, encryption at rest, creation, verification, restore, automatic/manual retention, corruption detection, and deletion. Schedule tests cover cron parsing, action permissions, encrypted console-command storage and dispatch, API redaction, backup worker outcomes, start/stop dispatch and skipped outcomes, restart countdown ordering/cancellation, online-player skipping, query-failure continuation, background execution, and run history. Notification tests cover admin-only access, encrypted storage, HMAC signatures, webhook delivery, and redirect rejection. Loopback browser smokes loaded the per-server restart options, saved a restart with a one-minute warning and a 2027 next run, confirmed it in the list, showed the player-count checkbox for Minecraft Java, and opened the encrypted console-command form without saving it. Docker lifecycle and console execution remain unverified against a live game server in this environment. Backups remain host-local. SFTP, SMB, S3-compatible targets, other scheduler actions, and realm/global scheduling remain unimplemented.

An administrator can configure one signed outgoing webhook for `backup.success` and `backup.failure`, send a test event, and choose which events to receive. The URL and optional HMAC signing key are encrypted with `auth.secret_key`; responses reveal only whether each is configured. Redirects are not followed; HTTPS is required except localhost loopback testing. Discord, Telegram, SMTP, and other event types remain unimplemented.

Runtime monitoring records confirmed container exits and repeatedly confirmed missing containers for servers Docklight marked as running. It waits 60 seconds after panel startup, requires a healthy Docker ping, and confirms the same stopped/missing observation at least 15 seconds later. Unknown Docker errors leave the last known server state unchanged. Confirmed incidents set the server to **Needs attention**, preserve server data, and appear in the per-server **History** tab. The latest 50 incidents are shown and 100 retained. Administrators can opt into a signed `server.crash` webhook with the server name and incident details. Runtime tests cover startup grace, Docker outages, exit/missing confirmation, RBAC, startup exits, deletion cleanup, data preservation, and webhook delivery. Planted faults bypassing debounce or changing the webhook event name caused the corresponding tests to fail. Browser verification used seeded incident data; Docker Engine was unavailable for a live crash test. Query-based automatic recovery is documented separately below and still needs Docker-host acceptance.

Low-disk monitoring checks the filesystem containing Docklight's data directory every five minutes. It sends the opt-in `host.disk_low` webhook below 10% free and rearms at 15%; its message reports capacity and names server-data and local-backup paths. The admin Notifications page reports current capacity and alert state. Tests cover threshold edges, repeat suppression, rearming, persistence, and webhook delivery. A planted inclusive-boundary fault made the threshold test fail at exactly 10%; after restoring the strict threshold it passed. Other mounted filesystems are not enumerated, and no files are automatically deleted.

Automatic recovery is opt-in per server and limited to templates with player-query support. The watchdog probes every 20 seconds with a 3-second timeout, requires three consecutive failures, and applies a four-minute cooldown after each recovery attempt. It retries a failed restart up to three times with 15-second spacing. Cooldowns and successful heals are persisted so a panel restart does not reset the 30-minute quarantine window. Five successful recoveries within 30 minutes put the server in quarantine; manual start or stop clears the quarantine. The specification appendix uses both “more than five” and “five” as its threshold; this implementation quarantines after the fifth successful recovery. Deterministic tests cover startup grace, Docker unavailability, the failure threshold, healthy-probe reset, cooldown across monitor-state reloads, retries and manual cancellation, webhook delivery, access checks, query-protocol eligibility, and quarantine while a new start is still progressing. No live Docker engine was available for restart acceptance.

The UI assets are embedded and have no CDN or frontend package dependency. It is a compact HTML/CSS/JavaScript app rather than the specified Svelte/Tailwind build. It has light and dark themes, but no offline service worker or complete installable PWA.

The template and config readers intentionally accept a bounded subset of YAML rather than general YAML 1.2. Unknown template fields are ignored, so stack/backup fields from other implementations do not create working behavior here. JWT signing and WebSocket framing are implemented locally because the corresponding requested dependencies were unavailable offline. These substitutions are recorded in [DECISIONS.md](DECISIONS.md).

## Environment limits and remaining acceptance work

- Docker CLI and daemon are absent here. A Minecraft server install/start/ready/query/console/graceful-save cycle, Vaultwarden and Uptime Kuma browser access, and app-stack behavior remain unverified.
- This environment denies local TCP/UDP binds, so the network fixture tests are skipped by default. Set `YGGDRASIL_TEST_NETWORK=1` on a host that permits loopback binds to run them.
- `install.sh` syntax is checked but its package installation, systemd setup, and re-run preservation must be tested on a fresh Debian 12 or Ubuntu 24.04 VM.
- No release owner/repository is configured. The installer needs a source checkout, `YGG_BINARY_URL`, `YGG_BINARY_FILE`, or `YGG_REPO` until release artifacts are published.
- The Docklight UI and Backups tab were browser-smoke-tested at the default desktop viewport. Mobile breakpoints still need a separate browser pass.

Before calling Phase 1 accepted, run the Docker and installer acceptance steps from the user brief on a disposable Debian/Ubuntu host and verify the embedded UI in a browser.
